## 分析

### Gate 判定：通过，但是险过

按计划设定的门槛（5 人中 3 人以上说有用）：

| 朋友 | 判定 | 依据 |
|---|---|---|
| B | **明确有用** | 主动说出「可以帮忙避雷」，且注意到「comment 挺尖锐的」 |
| D | **明确有用** | 逐张评价完 23 张，18 张标为有用 |
| A | 偏正面 | 「很好呀」，但未举出任何具体例子，随即转向改进建议 |
| C | 保留 | 只看了 1 张就停下，标为「一半一半」，理由是缺价位 |
| E | **质疑可信度** | 未回答有用与否，而是追问 5 条评论的挑选原则与目标受众 |

**明确说有用的是 2 人。计划设定的门槛是 5 人中 3 人以上——没有达到。**

按计划原文，「少于 3 人 → 停下来。回头看是 prompt 问题还是方向问题。」

**回头看的结论：既不是 prompt 问题，也不是方向问题，是可信度呈现的问题。**

没有任何一个人说信息本身没有价值。B 明确认可核心卖点，D 逐张看完并给出 18 张有用。
反对意见集中在三处，全部与「信息怎么来的」和「怎么呈现」有关，没有一条是
「这些信息我不需要」：

- C：缺价位（数据缺失，根因是 Places API 未接入）
- E：不知道 5 条评论怎么选的、不知道做给谁看的（**方法论未公开**）
- A、E：界面观感差（呈现问题）

因此判定为：**第一轮 Gate 未通过。不改方向，改透明度与呈现，然后重测。**

这与「硬着头皮继续」是两回事——继续做第 2 周的批量管线没有意义，
如果用户根本不知道该不该信这些卡片，铺到 150 家店只是把不可信的东西做得更多。

### 最强的正面信号：差异化被自发感知到

朋友 B 的原话是「**可以帮忙避雷**」——「避雷」这个词是他自己说的，没有被提问引导。

而「这些 comment 还挺尖锐的」说明他注意到了「慎选」字段与常见点评产品的区别。

这是 [README 决策 3](../README.md)（把「慎选」放在最显眼位置）**第一次得到用户端的验证**：产品的差异化不需要解释，用户自己读得出来。

### 最重要的负面信号：价位缺失

朋友 C 只看了 1 张就停下，理由是「我最好奇的价位你没标注」。

**这是第三次有人提到价位：**

| 来源 | 原话 |
|---|---|
| 受访者 01（访谈） | 「可以直接罗列菜品**和价格**和真实评价」 |
| 受访者 03（访谈） | 「列出地址、**价位**、营业时间、客户评价」 |
| 朋友 C（Gate） | 「我最好奇的**价位**你没标注」 |

定 schema 时明确砍掉了菜品价格字段，理由是「评论里极少出现具体菜价，店铺级人均价位由 Places API 直接返回，不需要 LLM 抽」。**这个判断本身没错，错在 Places API 至今没接上，所以那个字段是空的。**

用户看不到内部原因，他们只看到「没有价位」。

### 两条反馈指向同一个根因

| 反馈 | 来源 | 数据在哪 |
|---|---|---|
| 「价位你没标注」 | 朋友 C | Places API 的 `priceLevel` |
| 「有图片就更好了」 | 朋友 D | Places API 的 `photos` |

**这两样都不是 LLM 提炼的产物，而是 Places API 直接返回的结构化数据。**

结论：**Google Cloud 支付验证不解决，产品的可感知价值就上不去。** 它从「一件烦人的行政事务」升级为「用户验证过的头号阻塞项」。

### 朋友 E 提出的三个问题，逐条回应

#### 「5 条公开评论，不知道你的挑选原则是什么，随机挑选的吗」

**这是整轮反馈里最尖锐的一句，而且它戳中的是产品的根基。**

实际规则是：取 Google 地图**默认排序（最相关）的前 5 条**，不做任何人工挑选。
之所以是 5 条，是为了模拟 Places API 的返回上限（每店约 5 条），
使手动降级通道产出的数据与将来自动管线一致。

**但这条规则从未出现在页面上。** 卡片只写了「由 5 条公开评论自动提炼」，
没说是哪 5 条、怎么来的。

后果是致命的：整个产品的可信度机制建立在「N/5 条评论提到」这个计数上，
而**如果用户怀疑这 5 条是我挑的，那么所有的计数、所有的「慎选」都失去意义**。
一个合理的读者会默认最坏情况——他确实这么做了。

**这不是用户没看懂，是我没说。** 必须在卡片上明确标注取样规则。

#### 「不知道受众群体是谁，因为我看大部分是亚洲的」

目标用户在 [README 第二节](../README.md)里写着：在悉尼 1–2 年的中国留学生与
年轻工作者。所以选店偏华人餐厅**是符合定位的**。

但这一轮的 23 家店偏向华人餐厅还有另一个原因——刻意加入含中文评论的店，
用来验证「菜名保留原语言」的规则（见[数据质检报告](../docs/data-quality.md)）。
**这是技术测试的取样动机，不是产品定位的体现，两者恰好重合了。**

同样地，页面上没有任何一句话说明这是给谁做的。用户只能从店铺列表反推，
于是产生了「这到底是给谁看的」的疑问。

#### 「这个语言，一阵子英文一阵子中文的」

这是真实的阅读体验问题，而且每一处混杂都是有意设计的结果：

| 元素 | 语言 | 为什么 |
|---|---|---|
| 字段名与结论 | 中文 | 目标用户是中文读者 |
| 菜名 | 保留评论原文 | 用户要拿着菜名对照菜单点菜，菜单上印的是 `Bulgogi` 不是「韩式烤肉」 |
| 评论原句 | 逐字保留原文 | 可回 Google 核对，翻译过就不可核查了 |

**每条规则单独看都成立，叠在一张卡片上就成了阅读障碍。**

呈现层的解法：把评论原句默认折叠，点击才展开。原句是「证据」而非「正文」——
需要核对的人点开，不需要的人不必被迫阅读。这样既保留可核查性，
又消除大部分语言跳动。

### 其他

- **「增加搜索会更方便」（朋友 A）**——正是第 4 周的计划内容，说明方向判断正确，无需调整。
- **界面观感**——朋友 A：「过于黑暗调，看着不是很有食欲」；同一轮对话中另有一句「看着很难受是吧」。**两人提到，不再是个人口味问题。** 测试页面跟随系统主题，他们的手机是深色模式。餐饮类产品用深色会抑制食欲，第 3 周做前端时应默认浅色、不跟随系统深色。
- **朋友 D 的 4 张「一半一半」**：Beijing Impression、Fireside、Henry Lee's、The Best Taste of Asia。**唯一的「没用」是 Zhou Mum Cafe** —— 该店卡片的必点为 0 条，只有 1 条慎选和 2 条适合，是全部 23 张里内容最稀薄的一张。**这与「产出条目数过少的卡片不值得展示」的假设一致**（见 [数据质检报告](../docs/data-quality.md) 发现 4）。

### 朋友 E 的两条补充建议

#### 「中国餐馆可以涵盖其他 social platform 的评价」

**这条不采纳，但他指出的问题是真的，而且比他以为的更严重。**

不采纳的理由已经定过：小红书没有公开 API，爬取违反其服务条款。
这个项目要挂在简历上给面试官看，建立在违规爬取之上会是减分项。
Google Places 是唯一合规、有官方 API 的评论源。

**但他背后的直觉是对的：Google 评论对华人餐厅的覆盖确实不足。** 用现有数据验证：

| 范围 | 中文评论占比 |
|---|---|
| 全部 23 家店 · 115 条评论 | **13%** |
| 店名含中文的 9 家华人餐厅 · 45 条评论 | **20%** |
| 牛一碗 Lanzhou Beef Noodles | **0 / 5** |
| 杨国福麻辣烫 | **0 / 5** |

兰州拉面和麻辣烫这类客群几乎全为华人的店，Google 上一条中文评论都没有。

**这构成一个结构性局限：目标用户是在悉尼的华人，但数据源里中文的声音只占两成。**
卡片提炼出的「必点」「慎选」，主要反映的是非中文使用者的体验。

（需要说明的是，语言不等于族裔——很多华人也用英文写 Google 评论，
所以这个数字只能说明「中文评论稀少」，不能直接推出「华人不在 Google 上留言」。）

**处理方式**：不改数据源，但必须写进 README「数据来源与合规考量」一节，
作为已知局限主动披露。这与整个项目「主动暴露边界」的做法一致。

#### 「点评完了其他人去了，觉得符合你的评价会给你点个赞」

**方向很好，但现在做不了，记入 Roadmap。**

他描述的是一个由后来者验证前人评价的反馈闭环。对这个产品来说它特别贴切——
**它恰好能解决他自己提出的可信度问题**：卡片准不准，不由我说了算，
由去过的人投票修正。而且它不需要引入新数据源，边际成本为零。

做不了的原因是冷启动：现在有 0 个用户，没有人能验证任何东西。

**但有一个零成本的近似版本可以现在就规划进第 4 周。**
原计划的埋点里已经有「这条信息有用吗 👍👎」按钮，把提问改一下即可：

- 原设计：「这条信息对你有用吗？」——问的是**观感**
- 改为：「你去过这家店吗？卡片说得准吗？」——问的是**事实**

后者收集到的是可以直接用来修正卡片的信号，而前者只能得到一个满意度数字。
这是一次文案改动，不是新功能。

### 朋友 F 的两条，其中一条推翻了已有决策

#### 「你的评论很多都是 1/5，那是信还是不信啊」

**这一句推翻了[决策 5](../pipeline/prompts/v1.md)。**

原决策是：慎选门槛设为「1 条评论提到就写，但必须标注 `1/5`」。
当时评估过三个方案，选它的理由是「门槛设 2 条则大部分店慎选栏为空，
差异化消失；标注次数把判断权交还用户」。

**「把判断权交还用户」听起来很诚实，实际上是把难题丢回给了用户。**
用户看到 `1/5` 依然不知道该怎么办——这正是 F 的原话在问的事。

用现有数据看这个问题有多大：

| | 1/5 | ≥2/5 |
|---|---|---|
| 慎选 28 条 | **24 条（86%）** | 4 条 |
| 必点 64 条 | **53 条（83%）** | 11 条 |

**卡片的主体内容就是「只有一个人这么说」。** 这不是边缘情况。

而当初被否决的「提高门槛到 2 条」，现在有了数据，确认走不通：

| | 家数 |
|---|---|
| 现在慎选就为空的 | 7 |
| 提高门槛后会变空的 | 13 |
| **合计** | **20 / 23 = 87%** |

**两条路都堵死了：不标注不行，只标注也不行，提高门槛更不行。**

第三条路——**分层**，即当初评估时的方案 C，被以「schema、前端、数据库都多一层」为由否决。
现在有了用户证据，这个成本值得付：

- **≥2 条 → 「慎选」**：多人共识，红色显眼，值得当回事
- **1 条 → 「有人提到」**：单人经历，灰色次要，看一眼原文再判断

**关键在于：分层本身就是产品替用户做的那一层判断。**
F 要的不是更多信息，是「你告诉我这条该不该当回事」。
分层给了他这个答案，同时没有隐藏任何信息。

**成本很低**：`提及` 数字已经在数据里，**渲染层直接按 ≥2 / =1 分组即可，不需要改 prompt、不需要重跑 23 家店**。
先在渲染层验证有效，再决定要不要落进 schema。

#### 「统一一下推荐的标准：外卖支持与否，儿童宠物友好与否，人均价格，上菜速度」

他指出的是另一个真问题：**现在每家店的卡片结构都不一样，无法横向比较。**

根源在于「有依据才写，没依据就留空」这条原则——它对可信度是对的，
但产生的卡片没有统一骨架，两家店摆在一起没法比。

但他列举的四项里，性质并不相同：

| 项目 | 性质 | 应该从哪来 |
|---|---|---|
| 外卖支持 | 确定的事实 | **Places API 结构化字段** |
| 儿童 / 宠物友好 | 确定的事实 | **Places API 结构化字段** |
| 人均价格 | 确定的事实 | **Places API 结构化字段** |
| 上菜速度 | 主观体验 | 评论提炼（现有 `vibe` 字段） |

**前三项根本不该由 LLM 从评论里猜，Places API 直接就有。**
这是第三位用户指向同一处缺口（朋友 C 要价位、朋友 D 要照片、朋友 F 要这四项）。

第四项「上菜速度」已经在 `vibe` 里，但只有 8/23 家有——因为评论没提就留空。
可改为显式显示「评论中未提及」，让卡片骨架保持一致。这也是「统一标准」的一种实现，
且不违反「不许编」的原则。

## 关于测试方法本身的教训

4 人中只有 1 人用完了投票功能，1 人只投了 1 张，2 人完全没投。

**23 张卡片对一次用户测试来说太多了。** 没有人有义务读完 23 家店的信息。下一次应该只给 5 张，并且优先给对方去过的店——这样他既有判断依据，负担也小。

投票功能的价值不在于收集数据，而在于它暴露了这一点：**行为比嘴诚实。朋友 C 说的话（只看 1 张就停）比他点的按钮更有信息量。**
