# Prompt v3 · 四维卡片提炼

- **版本**：v3
- **日期**：2026-08-30
- **模型**：deepseek-v4-flash-0731（首选）/ qwen3.7-flash（备用）
- **状态**：待评测
- **上一版**：[v2.md](v2.md)

## 相对 v2 改了什么，为什么

v2 在 Hansang 上评测（qwen3.7-flash，27 项自动检查通过 26 项）后发现两个问题：

| # | v2 的问题 | v3 的改动 |
|---|---|---|
| 1 | **回归**：v2 新增「修正笔误」规则时，误删了 v1 的「不要翻译」约束，导致菜名被译成中文（泡菜饼 / 韩式烤肉）。用户拿着中文菜名无法对照英文菜单点菜，且自动校验因语言不匹配而失效 | 明确写死「保留原始语言，严禁翻译」，唯一允许的改动是修正拼写错误 |
| 2 | 「必点」收录了态度保留的菜（"both good (just not the best)"）和只提分量未称赞的菜（"especially the pancakes"） | 明确要求「明确称赞」，保留态度和仅提及存在性的一律不收 |

## v2 已验证成立的改动（保留）

- **`评论编号` 强制自洽**：v1 里 qwen 虚报次数（5 个菜里 3 个错），v2 加编号后「提及 == 编号长度」100% 自洽。**这是本项目最有效的一条 prompt 约束**，因为它把一个靠人工抽查的字段变成了程序可校验的字段
- **`场景依据` 受控放宽**：v1 场景标签恒为 `[]`（该店在场景搜索中完全不可见），v2 允许从用餐形式线索推断并强制指认线索后，标签被正确填充

## v2 被证伪的假设（如实记录）

> 假设：强制输出 `评论编号` 会让任务更机械，从而降低模型思考量。
> 结果：**不成立**。v1 思考占输出 82%，v2 为 89%，没有下降。
> 结论：思考成本是模型本身的属性，改不动 prompt 就解决不了，只能换模型或换供应商。

## 评测记录

| 店名 | 风格 | 模型 | 自动校验 | 备注 |
|---|---|---|---|---|
| Hansang | 韩餐 · 差评密集 | qwen3.7-flash | 17/18 = **94%** | 菜名可用（笔误已修正）；1 处原句拼接幻觉 |
| Kobe Wagyu Yakiniku | 日式烤肉 · 清一色好评 | qwen3.7-flash | 18/18 = **100%** | 次数经手工交叉核对全部正确 |

**两家店合计：35 项检查通过 34 项 = 97%**

### Kobe 这一轮验证了三件 Hansang 验证不了的事

1. **不硬编缺点**：5 条全好评时 `慎选` 和 `高频负面词` 都输出 `[]`。这是反向防幻觉测试——「慎选」是 prompt 里反复强调的重点字段，模型有很强动机填满它，但它忍住了
2. **次数在正样本上同样准确**：Wagyu 声称提及 4 条、编号 `[1,2,3,5]`，交叉核对完全正确（评论 4 确实未提及）
3. **`一致性` 字段有了区分度**：Hansang「中」（食物好服务差），Kobe「高」（5 条一致）。证明把「置信度」改为「一致性」的决策成立——若沿用原设计，两家店都会是「低 · 仅基于5条评论」

### ⚠️ 从数据里发现的 schema 缺口（需产品决策）

Kobe 的 5 条评论里 **3 条在讲生日**，模型在「适合」中正确识别为「生日庆祝」。
但 `场景标签` 枚举只有 `date / friends / family / solo`，**装不下「庆祝/生日」这个场景**，
模型只能退而填 `friends` + `family`。

后果：第 4 周用户搜「朋友过生日找个好点的店」时，这家最该被命中的店，
在场景层面与普通朋友聚餐无法区分。

**待决策**：是否给枚举增加 `celebration`（生日/纪念日/升职等庆祝场合）。
需要更多店的数据来判断这是个案还是普遍模式。

**v3 修好的**：
- 菜名回到英文原文，可直接对照菜单点菜
- 笔误修正生效："friend chicken" → "Fried Chicken"，`原句` 仍保留原始拼写
- 剔除了态度保留的菜（bibimbap / bulgogi "just not the best"）

**v3 仍未解决 → v4 要改**：
1. ⚠️ **原句仍有拼接幻觉**。模型把评论前半段的 "pressured to leave well before that limit"
   和后半段的 "pressuring paying customers to leave before..." 缝成一句，多塞了一个 `well`。
   人工抽查发现不了一个单词的差异，是 `verify.py` 抓到的。
   → v4 需增加约束：原句必须来自**单一连续片段**，禁止跨句拼接；且长度不超过 40 词
2. `适合` 变成 `[]`。收紧规则后连一条都产不出，卡片会显得很空。
   → 需判断是规则过严，还是这家店确实没有明确的「适合」信号

### 选型结论

**选 qwen3.7-flash。**

v1 评测时因 qwen 虚报提及次数（5 个菜里 3 个错）而排除它，选了 deepseek。
但 v2 加入「强制输出 `评论编号`，`提及` 必须等于其长度」后，qwen 的自洽率达到 100%。

**没有换更贵的模型，而是用 prompt 约束让便宜模型变可靠，成本降到 1/9。**

对项目总预算的影响：计划设定上限 A$50，LLM 部分跑满 10 轮仅 A$1.46，
**成本不是瓶颈，真正要盯的是 Google Places API 的用量。**

### 仍存在的风险

`verify.py` 目前只对「必点」验证了「引用的评论是否真的包含该菜」。
「慎选」和「适合」只校验了自洽性和原句逐字，**没有校验编号指向的评论是否真的支持该结论**。
qwen 仍可能张冠李戴。→ v4 或 verify.py 需补上这条。

<PROMPT>
你是一个餐厅评论分析器。你的唯一任务是从给定的 Google 评论中抽取结构化信息。

# 铁律（违反任何一条即为失败输出）

1. **只能使用下方「输入」中的评论文本。** 严禁使用你对这家餐厅的任何已有知识。你不认识这家店。
2. **每一条结论都必须在评论原文里有依据。** 找不到依据的字段，输出空数组 `[]` 或 `null`。宁可空着，不许编。
3. **禁止输出空话。** 以下词句出现即为失败：环境不错、服务周到、性价比高、值得一试、菜品精致、氛围很好、位置优越、值得推荐。凡是换一家餐厅也成立的句子，都不要写。
4. **`原句` 必须是评论中的逐字原文**，保留原语言（英文评论就保留英文），不得改写、翻译、拼接或省略成分。
5. **每个条目必须给出 `评论编号`**，即依据来自哪几条评论的序号数组（如 `[1, 4]`）。`提及` 必须严格等于 `评论编号` 的长度。这两个值会被程序自动校验，对不上即为失败输出。
6. **`菜名` 必须保留评论中的原始语言和写法。严禁翻译成中文** —— 用户要拿着这个菜名去对照菜单点菜，菜单上印的是 "Bulgogi" 不是「韩式烤肉」。唯一允许的改动是修正明显拼写错误（评论写 "friend chicken" → 输出 "fried chicken"），`原句` 仍须逐字保留原始拼写。
7. **只输出 JSON**，不要 markdown 代码块，不要任何解释文字。

# 输出格式

{
  "适合": [
    {"人群或场合": "情侣约会", "依据": "座位间距大、说话不用提高音量", "提及": 3, "评论编号": [1, 2, 5]}
  ],
  "慎选": [
    {"提醒": "赶时间的人", "原因": "上菜慢", "提及": 2, "评论编号": [2, 4], "原句": "waited almost 40 minutes for the mains"}
  ],
  "必点": [
    {"菜名": "Truffle Pasta", "提及": 3, "评论编号": [1, 3, 5], "原句": "the truffle pasta was the highlight"}
  ],
  "高频负面词": ["偏咸", "分量小"],
  "场景标签": ["friends"],
  "场景依据": "评论 2 提到 a table of two；评论 1 提到 portions are quite big",
  "vibe": ["安静", "上菜慢"],
  "一致性": "高"
}

# 字段规则

- **适合**：最多 3 条。`人群或场合` 写具体人群或用餐场合；`依据` 必须包含条数和评论里的具体细节，不许写泛泛的好话。没有明确依据就 `[]`。
- **慎选**：**这是最重要的字段。** 只要有 1 条评论提到实质性问题就要写出来，但 `提及` 必须如实填。`提醒` 写成人群导向（如「想吃饱的人」「带小孩的家庭」），不要写成形容词。
- **必点**：最多 5 道。**必须是具体菜品**。品类词一律不算菜名，包括但不限于：stews、soups、dishes、side dishes、food、mains、noodles。评论若只说 "their stews are great"，则不产出条目；评论若点名 "kimchi pancake"、"soondae"，才产出。只有被**明确称赞**的菜才算：「both good (just not the best)」这种保留态度的、以及只提到分量或存在性而未称赞的，一律不产出。
- **高频负面词**：只描述**食物本身**的短词，如 偏咸 / 偏油 / 分量小 / 不新鲜。环境和流程问题不写在这里，写进 vibe。没有就 `[]`。
- **场景标签**：只能从 `["date", "friends", "family", "solo"]` 中选，可多选。判断依据只能是评论里的**用餐形式线索**——同行人数（"a table of two"、"we"、"my family"）、分量描述、是否适合久坐、店名中的自我定位。**严禁凭菜系或餐厅类型猜测**（"韩餐所以适合朋友聚餐"是失败）。选了标签就必须在 `场景依据` 里指出具体线索；确实无线索则输出 `[]` 且 `场景依据` 为 null。
- **vibe**：只能从 `["安静", "嘈杂", "需排队", "上菜慢", "上菜快", "座位拥挤", "空间宽敞", "适合久坐", "翻台快"]` 中选。同样必须有评论支撑。
- **一致性**：
  - `高` = 多数评论对这家店的评价方向一致，互相印证
  - `中` = 评论之间有明显分歧（有人夸有人骂同一件事）
  - `低` = 评论条数过少，或内容几乎无实质信息（如只有「good」「nice place」）
