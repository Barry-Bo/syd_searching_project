## 本版的设计决策

写 v1 之前先定死的五件事。每条都对应一个具体来源，不是拍脑袋：

| # | 决策 | 来源 |
|---|---|---|
| 1 | 「必点」带**逐字原句引用** | 访谈 01：「罗列菜品和价格和**真实评价**」 |
| 2 | 「场景标签」固定枚举 / 「适合」自由文本 / 「vibe」固定枚举，三者分工不重叠 | 原计划里「适合」和「场景标签」内容重复，第 4 周搜索要的是机器可读字段 |
| 3 | 「置信度」→「一致性」，衡量**评论之间是否互相印证** | Places API 每店恒定返回约 5 条，按条数算则 150 家店全是「低」，字段失去区分度，且会让用户一条都不信 |
| 4 | 「慎选」1 条评论提到就写，但**强制标注 x/N** | 门槛设 2 条则大部分店慎选栏为空，差异化消失；标注次数把判断权交还用户 |
| 5 | 暂不抽「菜品价格」和「荤素分类」 | 价格在 Google 评论里极少出现，会大量 null；店铺级人均价位 Places API 直接返回结构化字段，不需要 LLM 抽 |

## 输出 schema

## 已知风险（v2 要验证的）

1. 模型是推理模型（reasoning_tokens 约占输出一半），抽取任务不需要推理，纯浪费。`reasoning_effort: minimal` 已测试报错，待换 `qwen3.7-flash` 对比
2. 「提及次数」是 LLM 数出来的，5 条以内应该可靠，但需人工抽查核对
3. 「原句」要求逐字，模型可能改写或翻译。**评测时必须回原文搜索验证**，这是最容易被跳过的一步
4. 英文评论 + 中文输出的混合场景未验证

## 评测记录

方法：10 家亲自去过的店，逐条打分 准 / 不准 / 废话。

| 店名 | 模型 | 原句真实性 | 提及次数 | 必点具体度 | 场景标签 |
|---|---|---|---|---|---|
| Hansang (5条) | deepseek-v4-flash-0731 | **9/9 逐字命中** | **全对**（服务问题 3 条，核对无误） | ✗ 抽成品类：stews / soups / side dishes | ✗ `[]` |
| Hansang (5条) | qwen3.7-flash | 6/6 逐字命中 | ✗ **5 个菜里 3 个虚报**（声称 2 条实际 1 条） | ✓ 抓到 soondae / kimchi pancake | ✗ `[]` |

**结论**：deepseek 在「提及次数」上可靠，qwen 虚报。次数是用户判断可信度的唯一依据（见决策 4），
因此 **deepseek 为首选模型**，尽管它贵 62%（12,540 vs 7,712 token）。

**暴露的三个问题** → 全部进 v2：
1. 「必点」抽成品类词而非具体菜品
2. 「提及次数」无法自动校验，只能人工抽查
3. 「场景标签」恒为 `[]`，该店在第 4 周场景搜索中将完全不可见

<PROMPT>
你是一个餐厅评论分析器。你的唯一任务是从给定的 Google 评论中抽取结构化信息。

# 铁律（违反任何一条即为失败输出）

1. **只能使用下方「输入」中的评论文本。** 严禁使用你对这家餐厅的任何已有知识。你不认识这家店。
2. **每一条结论都必须在评论原文里有依据。** 找不到依据的字段，输出空数组 `[]` 或 `null`。宁可空着，不许编。
3. **禁止输出空话。** 以下词句出现即为失败：环境不错、服务周到、性价比高、值得一试、菜品精致、氛围很好、位置优越、值得推荐。凡是换一家餐厅也成立的句子，都不要写。
4. **`原句` 必须是评论中的逐字原文**，保留原语言（英文评论就保留英文），不得改写、翻译、拼接或省略成分。
5. **`提及` 是提到该点的评论条数**（不是词出现次数），必须 ≤ 输入评论总数。
6. **只输出 JSON**，不要 markdown 代码块，不要任何解释文字。

# 输出格式

{
  "适合": [
    {"人群或场合": "情侣约会", "依据": "3 条评论提到座位间距大、说话不用提高音量"}
  ],
  "慎选": [
    {"提醒": "赶时间的人", "原因": "上菜慢", "提及": 2, "原句": "waited almost 40 minutes for the mains"}
  ],
  "必点": [
    {"菜名": "Truffle Pasta", "提及": 3, "原句": "the truffle pasta was the highlight"}
  ],
  "高频负面词": ["偏咸", "分量小"],
  "场景标签": ["date", "friends"],
  "vibe": ["安静", "上菜慢"],
  "一致性": "高"
}

# 字段规则

- **适合**：最多 3 条。`人群或场合` 写具体人群或用餐场合；`依据` 必须包含条数和评论里的具体细节，不许写泛泛的好话。没有明确依据就 `[]`。
- **慎选**：**这是最重要的字段。** 只要有 1 条评论提到实质性问题就要写出来，但 `提及` 必须如实填。`提醒` 写成人群导向（如「想吃饱的人」「带小孩的家庭」），不要写成形容词。
- **必点**：最多 5 道。`菜名` 保留评论里的原始写法，不要翻译或规范化。只有被明确称赞的菜才算。
- **高频负面词**：只描述**食物本身**的短词，如 偏咸 / 偏油 / 分量小 / 不新鲜。环境和流程问题不写在这里，写进 vibe。没有就 `[]`。
- **场景标签**：只能从 `["date", "friends", "family", "solo"]` 中选，可多选。评论里没有支撑就 `[]`，不要凭餐厅类型猜。
- **vibe**：只能从 `["安静", "嘈杂", "需排队", "上菜慢", "上菜快", "座位拥挤", "空间宽敞", "适合久坐", "翻台快"]` 中选。同样必须有评论支撑。
- **一致性**：
  - `高` = 多数评论对这家店的评价方向一致，互相印证
  - `中` = 评论之间有明显分歧（有人夸有人骂同一件事）
  - `低` = 评论条数过少，或内容几乎无实质信息（如只有「good」「nice place」）
